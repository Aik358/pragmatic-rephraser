Task definition. The application receives one Chinese sentence as input, determines its speech act, and rewrites the same intention into several pragmatic variants, displayed side by side. The purpose of the system is to demonstrate that one and the same intention can be realised in different ways according to different politeness strategies.

The basic structure of the application is as follows.

Input. One Chinese sentence. The sentence may already contain politeness markers (请, 麻烦, 好吗); these must be handled rather than duplicated.
Speech-act identification. At minimum, the system distinguishes requests/instructions, criticisms, refusals, complaints, and suggestions. The recognised category is displayed together with the evidence — the words or patterns that triggered the decision.
Rewrite engine. For each speech act, the system produces variants in four tones: (a) Neutral Direct (直接): the bare statement or imperative, without politeness marking; (b) Polite (礼貌): conventional markers such as 请 / 麻烦你, interrogative framing (好吗？), and pre-thanking; (c) Very Polite (非常礼貌): the honorific 您, apologies (不好意思 / 打扰您一下), and hedges (不知道能不能 / 如果方便的话); (d) Indirect Hint (委婉暗示): the intention is never stated explicitly; the rewrite relies on situational cues or wish-frames (要是……就好了). These four tones correspond to the politeness strategies of Brown and Levinson (1987). Each variant is labelled with its strategy and accompanied by a one-line explanation of the linguistic devices it uses.
Invariants. Every variant must preserve the propositional content of the input: the system performs pragmatic variation, not paraphrase or translation. In particular, an Indirect Hint must never contain an imperative construction.
Interface. The variants are presented as cards, each showing the tone name, the strategy label, the rewritten sentence, and the explanation. Provide five or six example sentences that can be inserted with one click, including 把窗户关上. For this example the expected output is approximately: 把窗户关上。 / 麻烦你把窗户关上好吗？谢谢啦！ / 不好意思，打扰您一下。不知道能不能麻烦您把窗户关一下？非常感谢！ / 风好像有点大呢，这窗户还开着呀……
Technical constraints. The entire application must be a single index.html file with embedded CSS and JavaScript. No backend, no external dependencies; the file must run offline when opened directly in a browser. A rule-based, lexicon-based implementation in plain JavaScript is expected. The interface must be responsive and visually clean.

Output the complete code. Additional requirements — an optional LLM mode and a specific visual design — will be introduced after this core system has been reviewed.

# Diagnosis: why the system failed to identify an AI-generated message

**Scope note.** “The system” in this project is the single-file 语用改写器 (`index.html`): a rule-based speech-act classifier plus an optional LLM mode that calls OpenAI-compatible providers and returns free-text variants. **Neither component performs authorship detection.** So the failure is not a missed threshold — it is that no AI-detection pathway exists, and any attempt to “detect” relied on either an LLM judging itself or informal heuristics. Causes are ranked below, most likely first.

---

## Prioritized likely causes

### P1 — No detection component exists; detection was delegated to an LLM self-judgment
- **Evidence.** The codebase has no classifier, perplexity scorer, watermark check, or logprobs analysis. The only AI path is `callChatCompletion` returning text. If someone asked the LLM “is this AI-generated?”, the model was being used as its own detector.
- **Why it fails.** LLMs cannot reliably self-identify output: they have no introspection into sampling, and instruction-following judges are erratic. OpenAI retired its own AI Text Classifier after acknowledging very low reliability (widely reported ~26% accuracy on short or foreign-language text); the tool was quietly disabled ([Quetext](https://www.quetext.com/blog/openai-ai-text-classifier#1), [Indian Express](https://indianexpress.com/article/technology/artificial-intelligence/openai-pulls-the-plug-on-ai-classifier-8859266/), [澎湃新闻](https://www.thepaper.cn/newsDetail_forward_23997902)). A self-judge inherits that weakness wholesale.

### P2 — Statistical fingerprints of modern LLM output are nearly indistinguishable from human text
- **Evidence.** Sadasivan et al., *Can AI-Generated Text be Reliably Detected?* ([arXiv 2303.11156](https://ar5iv.labs.arxiv.org/html/2303.11156v4)) showed detectors degrade to near-chance under paraphrasing attacks; a NeurIPS 2025 paper frames adversarial paraphrasing as a *universal humanizing attack* ([poster](https://neurips.cc/virtual/2025/loc/san-diego/poster/116833)); even human-written paraphrases transfer into missed detections ([ScienceDirect](https://www.sciencedirect.com/science/article/pii/S2949719125000275)).
- **Why it fails for this case.** Current instruct-tuned LLMs produce low-perplexity, low-burstiness text that sits inside the human distribution — especially *short* sentences (this input is one line), where token-level statistics have almost no sample size to separate classes. The message carries none of the high-entropy phrase patterns that older detectors keyed on.

### P3 — Preprocessing destroyed whatever weak signal existed
- **Evidence.** The pipeline normalizes input before it is ever scored: whitespace collapsing, trailing-punctuation stripping, removal of 请/麻烦/好吗 surface markers, and a 160-character cap. These are exactly the operations that erase lexical and n-gram fingerprints; interrupted/truncated Chinese also breaks token streams. Detection run on the *display* string rather than the raw string removes the only usable statistics.
- **Also:** Chinese text (even with mixed Latin tokens like PPT/LLM) needs a per-language tokenizer; a Latin-trained detector gets near-zero signal on a Chinese sentence.

### P4 — No calibration / threshold logic (and, if a heuristic score existed, it would be mis-scaled)
- **Evidence.** There is no score output at all; the offline engine returns only a category and evidence list. Where detectors do exist, the deciding threshold is the derailment point: a conservative false-positive budget (e.g., 1% FPR) necessarily suppresses true positives on short texts, where confidence intervals are wide.
- **Recommendation-shaped corollary:** any added detector must report a confidence band and an “uncertain” zone per input length rather than a binary label.

### P5 — Detector/training-data generation gap
- **Evidence.** Published classifiers were trained on GPT-3-era distributions; each new generation (RLHF/instruction tuning) shifts the token distribution again. Chinese corpora are even thinner in most public detectors. This project additionally uses providers that (by default) expose no `logprobs`, so the standard perplexity-based detector cannot even be computed from the API response.

### P6 — Watermark absence at generation time
- **Evidence.** No provider configured here enables watermarking, and APIs don’t implement it implicitly. Cryptographic/text watermarking (Kirchner et al. 2023; DeepMind SynthID) is the only mechanism with *provable* attribution, and even SynthID has known probing/forge attacks ([eth-sri probing blog](https://eth-sri.github.io/blog/probingsynthid)). Without watermarking, detection is inherently statistical and therefore fallible.

### P7 — Message characteristics themselves
- The specific message is short, single-clause, and highly conventional (a request/politeness formula). The rephraser’s *point* is to make output look natural — the polite/indirect variants deliberately mimic human conversational patterns — so the output lands precisely in the “human-like” region of feature space. A generic single sentence provides no unusual co-occurrences, factual anchors, or stylistic deviation for any detector to hold onto.

---

## Recommended actions

1. **Stop using an LLM as its own detector.** If a judge is needed, use a *different* model with an explicit rubric and calibration — but treat the result as weak evidence only.
2. **Implement a real detection stack** (optional feature in the same single file):
- Request `logprobs` from the OpenAI-compatible endpoint and compute mean negative log-likelihood (perplexity);
- combine with a burstiness metric (variance of token surprisal) and, optionally, a small n-gram classifier;
- score **per language** (zh/en) with thresholds calibrated per input-length bin;
- return a confidence band (“likely human / uncertain / likely AI”) plus the rationale features.
3. **Fix the data path:** run detection on the **raw** input before marker-stripping and truncation; require ≥ a meaningful token window (e.g., warn below ~200 tokens); never reuse normalized display text for scoring.
4. **Add generation-time watermarking** where the provider supports it (or note which providers do), so attribution is provable rather than statistical.
5. **Evaluate honestly:** report AUROC / recall at a fixed FPR on a current-generation Chinese test set; review by humans in the “uncertain” band.
6. **In-UI:** if an “AI 疑似度” readout is added, label it clearly as statistical plausibility, not proof.

Key sources: [Sadasivan et al. 2303.11156](https://ar5iv.labs.arxiv.org/html/2303.11156v4), [NeurIPS 2025 adversarial-paraphrasing poster](https://neurips.cc/virtual/2025/loc/san-diego/poster/116833), [Paraphrase-transfer effects study](https://www.sciencedirect.com/science/article/pii/S2949719125000275), [OpenAI classifier retirement coverage](https://www.quetext.com/blog/openai-ai-text-classifier#1), [SynthID probing](https://eth-sri.github.io/blog/probingsynthid).
